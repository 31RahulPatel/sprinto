- [x] New flow, identical in both modules: `POST :id/evidence/presign` (authorizes via the existing `canUploadEvidence`/`canUploadTaskEvidence`, returns a short-lived signed PUT URL — **no DB row created yet**) → browser `PUT`s the file bytes straight to S3, bypassing both Next.js and Nest → `POST :id/evidence/:evidenceId/confirm` (re-authorizes, `HeadObject`s the key it deterministically recomputes itself — never trusts a client-supplied key — to read back the *real* size/content-type, deletes-and-rejects if over the 10MB cap, only then creates the `Evidence` row). An abandoned/failed upload never leaves an orphaned DB record. Download: `GET :id/evidence/:evidenceId/file` now returns `{ url }` (a signed GET URL) instead of streaming; the Next.js route 302-redirects the **browser** to it (not itself, so the bytes never pass through the Next.js server either)
- [x] Frontend: `EvidenceUploader.tsx` (shared by Findings/Tasks/StaffDevice checks via its `basePath` prop) rewritten into the 3-step presign→PUT→confirm sequence, keeping the existing upload progress bar on the actual S3 PUT. `EvidenceList.tsx` needed **zero changes** — its `<a href>`/`<img src>` pointing at `.../file` keep working unchanged since browsers transparently follow redirects for navigation/image loads, no CORS needed for that direction
- [x] **Accepted tradeoff, documented in code**: a presigned `PutObjectCommand` can't enforce a byte-size cap the way a presigned POST policy's `content-length-range` condition could — the 10MB cap is instead enforced retroactively in the `confirm` step (delete + reject if oversized). Presigned POST would close that gap but adds real complexity (multipart form fields + policy generation) not worth it for this
- [x] Verified: backend `npm run build` and frontend `npx tsc --noEmit`/`eslint` all clean; grepped for leftover `FileInterceptor`/`putObject`/`getObjectStream`/multipart-form-upload references (none)
